Prerequisites

Confirm these before touching the repo — the setup script will refuse to run without them, and Python 3.13 specifically is rejected.

Any recent version works.
Must be the docker compose subcommand, not the old standalone docker-compose binary — runs Postgres/TimescaleDB and Qdrant.
docker compose version
Expect
Prints a version number, no "command not found".
3.13 is explicitly rejected by scripts/setup.sh — check before you start, not after a failed run.
python3 --version
For the React frontend.
node --version
Only needed if you're also testing the AI-labelled items in Phase 6. Skip for the core pass.

Five different question shapes, to see the assistant route each one to the right evidence.

Expect

Expect

Expect
Pulls in the root cause / outcome summary that was actually saved on that case — not a generic answer.

Optional — local AI AI

Everything in Phases 0–5 works with zero AI, zero API keys. This turns on a self-hosted Ollama model — every item here is additive: the deterministic behavior from earlier phases must still work exactly the same underneath it.

docker compose --profile ai up -d
# then, in the same terminal that runs the app:
OPS_SIGNALS_AI_ENABLED=1 OPS_SIGNALS_AI_PROVIDER=ollama ./scripts/run_all.sh
Expect
Pulls a small model (~2GB) on first run.
Findings → open the same finding's View Details a second time.
Expect
A small AI badge next to a rewritten summary, appearing ~1–2s after opening.
Repeat the recommendation evaluation from Phase 2.
Expect
A "Second Opinion" panel appears below the results, with a note if it disagrees with the router's own pick.
Open Behavior Intelligence and select a detected behavior, if one exists.
Expect
A plain-language explanation of why the behavior matched, grounded in the same facts shown elsewhere on the page.
Note
Behavior findings need correlated activity across multiple metrics — a single lab scenario may not produce any. Empty is expected, not a failure, if Phase 3 didn't trigger a cross-metric pattern.
Not wired to a button yet — call it directly. Get the case ID from the case page's URL (e.g. /cases/7 → ID is 7):
curl -X POST http://localhost:8001/api/cases/7/rca/suggest
Expect
{"available": true, "draft": "..."} — a suggested root cause. Re-check the case afterward: root_cause_summary must be unchanged. This only ever drafts; PATCH /rca is still the sole way to actually save one.
Same case ID as above:
curl -X POST http://localhost:8001/api/cases/7/resolution/suggest
Expect
A draft built from the case's own notes/RCA — never invented facts. {"available": false, ...} is the correct response if the case has no notes or RCA to draft from yet.
Repeat one of the Phase 5 questions.
Expect
More natural, specific phrasing than the fixed-template wording seen in Phase 5 — same grounding, same sources, better sentences.
Restart with ./scripts/run_all.sh (no OPS_SIGNALS_AI_* env vars this time), then revisit Findings, Behavior Intelligence, and Ask Ops Signals.
Expect
AI badges, the Second Opinion panel, and richer chat phrasing simply disappear. No errors, no blank pages, no missing data — this is the whole point of the fallback design.

Grafana plugin separate surface

A completely different UI — the same backend, run from inside Grafana instead of the standalone app. Different ports, its own build step, worth its own pass. Skip if only the standalone app is in scope.

Stop run_all.sh first if it's still running — this uses its own backend port.
./scripts/run_grafana_stack.sh
Expect
Builds the plugin bundle, then starts Grafana (:3000), Prometheus (:9090), mock metrics, and the backend (:8002) together. Ends with a "Press Ctrl+C to stop" line — that means it's up and running in this terminal.
In a second terminal:
curl -u admin:admin http://localhost:3000/api/plugins/ops-signals-app/settings
Expect
JSON response includes "id":"ops-signals-app" and "enabled":true.
Go to http://localhost:3000, log in with admin / admin, then open http://localhost:3000/a/ops-signals-app/ops-signals.
Expect
The Ops Signals toolbar renders inside Grafana. An "unsigned plugin" notice is expected for local development, not an error.
In the toolbar: Data source → Prometheus; Ops Signals backend → Local backend (:8002); Service → test-ruptures-abrupt-regime-shift; Metric → ops_signals_test_cpu_usage; Time range → Last 30m; click Run Analysis.
Expect
Sample count, signal count, findings, and a metric timeline appear. Run Details shows the same Recommended / Optional / Not Recommended / Rejected breakdown as Phase 3's Router Decisions — same engine, different frontend.
Click Create Case → step through Finding → Investigation → Root Cause → Resolution, saving at each step → open Publish Knowledge and click Republish knowledge.
Expect
Reopening the same finding reopens the existing case rather than duplicating it; memory_status moves toward indexed after publishing.
Click View all cases.
Expect
Lists the case just created (ID, status, updated time). The drawer should still open cleanly even if the list were empty.
Click a quick prompt like Which analyzers ran?, then type a custom question.
Expect
Analyzer-routing questions answer directly from the current run; broader questions fall back to documentation if historical memory is still empty.
