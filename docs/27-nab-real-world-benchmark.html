Analyzer routing · real-world evaluation

NAB Real-World Benchmark

Four labeled time series from the Numenta Anomaly Benchmark — real AWS, sensor, traffic and municipal data, not synthetic test fixtures — pushed through the live ops-signals pipeline (router → analyzers → signals) and checked against NAB's published anomaly windows.

Source: numenta/NAB · this repo already ships one NAB file as sample_data/ec2_cpu_utilization_24ae8d.csv — the four below are additional NAB series pulled for this run.

Strengths

  • Perfect window recall across all four series, 12/12. EC2 CPU, ambient temperature, and traffic speed hit every labeled window as-run; NYC taxi demand caught all 5 of its real demand shocks once the four fixes below shipped — see its section below for the full before/after.
  • Fast onset detection. On EC2 and traffic speed, the first matching signal lands within minutes of the window's own start — not just "somewhere inside it."
  • Cross-analyzer agreement. Where an anomaly is real, pyod_outlier and anomaly_zscore tend to fire together, and trend independently corroborates the traffic-speed slowdown as a sustained regression.
  • Best-case precision is strong. Ambient temperature reached 85% event precision (78 of 92 flagged points fell inside a real window) — proof the pipeline can be tight, not just sensitive.
  • Router reasoning is inspectable. Every routing decision ships eligibility/suitability scores and a plain-language reason, which is exactly what made the taxi gap possible to diagnose, fix, and re-verify from data alone — see #01/#03/#05/#06 below.

Weaknesses

  • Getting NYC taxi to full recall cost precision. Its event precision is now 33% (34 of 104 flagged points land in a real window) — pyod_outlier fires much more liberally once fed a de-seasonalized signal, and nothing yet trims the extra false positives. See #02/#07.
  • No re-baselining after a real shift. EC2 precision was only 41% — 20 of 34 flags are z-score comparing post-spike values against a pre-spike mean for a week afterward. Still open (#02).
  • Two recommended analyzers still have nowhere to run. darts and adtk can both score RECOMMENDED (1.00) with zero pipeline analyzer registered — #03 stopped them from crowding out real ones, it didn't give them anywhere to execute.
  • Ingestion rejected half the raw files. ambient_temperature and speed_7578 both failed default validation (max_gap_minutes: 60) before analysis could even start — real sensor/traffic feeds have bigger natural gaps than the default tolerates. Still open (#04).
01

Router: don't hard-gate anomaly analyzers on a "seasonal" profile

The suitability check requires an analyzer's supported profiles to intersect the series' detected profile. A series tagged seasonal/repeating_pattern scored every outlier analyzer NOT_RECOMMENDED before a single value was evaluated — this is what caused the 0/5 miss on taxi demand, and it would have recurred on any cyclic ops metric (traffic, checkout volume, request rate) with a real anomaly riding on top.

fixed & verified
Shipped: pyod_outlier/pyod are now exempt from the shape-mismatch cap — their supported profiles are irregularity-only, so a shape-only series label is no longer held against them. adtk stays excluded (its own scoring rules reward seasonality_strength directly, so shape genuinely is part of its job). Verified with a new regression test and a full re-run of benchmark/run_router_scenarios against the pre-fix baseline — zero regressions.
Combined outcome, verified on real data: on its own, this fix left nab_nyc_taxi's pyod_outlier score unchanged at 0.46 — the cap wasn't the binding constraint here, #05's feature-extraction gap was. Once #05 shipped too, this fix is what let the resulting 0.86 score actually count: profile_match flips to true and the +0.10 bonus applies, pushing it to RECOMMENDED. All four of #01/#03/#05/#06 were needed together to get NYC taxi from 0/5 to 5/5 windows recalled — see its section below.
02

anomaly_zscore needs to re-baseline after a detected shift

Once a level shift is confirmed (e.g. by baseline_shift), z-score should recompute its reference mean/variance instead of continuing to score new, now-normal values against the old baseline. This single change would have cut EC2's false positives from 20 to a handful.

high impact
03

Don't let a non-executable recommendation occupy an execution slot

recommended_threshold mode picks the top max_analyzers (3) by score, with no check that a candidate can actually run. darts/adtk can both score RECOMMENDED with no pipeline analyzer behind them, and were silently winning execution slots away from real analyzers that could have produced a finding.

fixed & verified
Shipped: candidate selection in recommended_threshold mode now filters to analyzers with a real, enabled pipeline mapping before ranking and capping — intelligence/pipeline.py's _available_pipeline_analyzer_ids. An existing test (test_recommended_threshold_selects_top_recommended_executable_analyzers) was already named for this promise but didn't enforce it — its own fixture proved the bug, then verified the fix. Full pytest suite: 325 passed, 0 regressions.
Verified on real data: on nab_nyc_taxi, this stopped darts/adtk (both non-executable, tied at score 1.0) from crowding pyod_outlier (0.86) out of the top-3 — a necessary link in the chain that got taxi to 5/5 windows recalled.
04

Make ingestion gap tolerance adaptive, not a fixed 60 minutes

Two of four real NAB files were rejected outright before analysis. Scale max_gap_minutes off the series' own detected interval (or raise the generic-provider default) so realistic sensor/traffic outages don't block ingestion by default.

medium impact
05

Compute spikiness/shift_index on a de-seasonalized residual, not raw values

This is the gap #01's fix actually exposed: on nab_nyc_taxi, real demand-shock anomalies never registered as "spiky" because spikiness is measured against the series' raw values, and the series' own large daily/weekly seasonal swing dwarfs the actual anomalies.

fixed & verified
Shipped: when seasonality is strong (seasonality_strength >= 0.42, the same bar already used elsewhere in this file), spikiness is now computed on values[t] - values[t - dominant_lag] — each point compared to the same point one cycle back — instead of the raw point-to-point jump. Falls back to raw-value behavior automatically when seasonality isn't detected or there's under one cycle of history. 5 new tests (including a direct real-data check before writing the synthetic ones); full benchmark/run_router_scenarios diff against baseline: zero regressions, despite this metric feeding 8 different analyzers' scoring rules.
Verified on real data: on nab_nyc_taxi, this alone took spikiness from 0.0 to 1.0 (max) and shift_index from 0.05 to ~1.0. Combined with #01 (lets a high score count) and #03 (stops it being crowded out), pyod_outlier reached RECOMMENDED (0.86) and, once #06 also shipped, actually executed.
06

Config-key mismatch silently dropped pyod_outlier from every real analysis run

Discovered while verifying #01/#03/#05 together: config/analyzers.yaml's override block for pyod_outlier used finding_rules (plural) — almost certainly copy-pasted from the anomaly_zscore block just above it — but PyODOutlierAnalyzer.__init__ only accepts finding_rule (singular). The extra kwarg raised inside instantiate(), and _build_analyzers' try/except silently swallowed it — pyod_outlier never constructed via the real provider=generic API path, no matter how the router scored it. Invisible until #01/#03/#05 finally got it selected for the first time.

fixed & verified
Shipped: renamed the key to finding_rule in config/analyzers.yaml. New regression test constructs every built-in analyzer through the exact same config path a real CSV upload uses (test_every_builtin_analyzer_constructs_under_the_real_generic_provider_config), so a reintroduced mismatch fails a test instead of silently vanishing from a live run.
07

NYC taxi's new false-positive rate (67% of its own events) needs its own look

Getting taxi to 5/5 window recall dropped its event precision to 33% (34/104) — far below the other three series. Worth a dedicated pass once #02's re-baselining logic exists, since the same "residual keeps flagging after the series has already reverted" pattern may be at play here too, just on the seasonal residual instead of the raw value.

NYC taxi demand

realKnownCause/nyc_taxi
30 min cadence · 10,320 raw points
windows recalled 5 / 5 events 34 matched events 70 false-positive event precision 33%

Five real demand shocks are on record — Halloween, Thanksgiving, the Christmas/New Year blizzard, and a January snowstorm. Originally the pipeline produced zero anomaly-type signals against any of them: pyod_outlier was capped by shape mismatch (#01), its spikiness evidence was itself masked by raw-value seasonality (#05), a tied non-executable recommendation was crowding it out of its execution slot (#03), and even once selected, a config-key typo silently kept it from ever constructing (#06). With all four fixed and re-verified against this exact series, pyod_outlier now scores 0.86 (RECOMMENDED), executes, and catches all 5 real windows — at the cost of 70 false positives among its 104 total flags (33% precision), which #07 tracks as the next thing worth tightening.

Overall quality: 82% — window-level recall 100% (12/12), up from 58% (7/12); event-level precision 55% (132/239), down from 73%, weighted 0.6/0.4 toward recall since a missed real incident costs more than a noisy one. The gain is real and verified, not estimated: it took four fixes together (#01 router cap, #03 execution-slot filtering, #05 de-seasonalized spikiness, #06 a config-key typo) to take NYC taxi from 0/5 to 5/5 windows recalled, re-run against the actual production API path each time. The remaining gap is precision, not recall — #02 and #07 are where the next points are.

Ground truth: NAB combined_windows.json, fetched 2026-09-15.
Pipeline runs: EC2/ambient/traffic executed via intelligence.cli run against the project's live Postgres/Qdrant stack; window-gap tolerance raised per-dataset only, all other config left at repo defaults. NYC taxi's final numbers were re-run through the actual production API path (POST /api/ingestion/csv-run, provider=generic, recommended_threshold selection mode) specifically because that's the path #01/#03/#05/#06 all needed to be verified against, not the looser CLI config.
Matching rule: a detection counts against a window if its [start, end] interval overlaps the window's published bounds; anything else is scored false-positive. Whole-series stumpy/prophet characterization signals are excluded — they describe the entire series, not a point in time.
